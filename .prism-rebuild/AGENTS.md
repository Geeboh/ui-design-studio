# PRISM rebuild operating instructions

## Objective and scope

Rebuild this UI Design Studio repository to the PRISM Studio 2.0 contracts. Complete M0–M8 and a verified release candidate. The authoritative work definition is `contracts/requirements.json`, `contracts/acceptance-cases.json`, the roadmap and the user's current instructions. These are rebuild instructions, not consumer-project defaults.

Read `START-HERE.md`, `docs/BUILD-ROADMAP.md` and the relevant requirement/contract subset. Load specialized references when the assigned task needs them. Do not repeatedly load the whole pack, book collection or repository. Existing repository instructions still apply; in particular, use installed Playwright Fast for browser work and real release browser matrices.

## Work autonomously and preserve authority

Continue routine authorized discovery, implementation, fixes, tests, local commits and documentation without repeatedly asking to continue. Resolve ordinary choices from the specifications. Record a material conflict, finish independent work, and ask only when required authority, credentials, an irreversible choice or unavailable required capability prevents progress. Do not invent permissions or waive failed requirements.

Use one goal/director. Parallelize independent bounded tasks; declare ownership and dependencies before dispatch. Serialize shared contracts, migrations, token definitions, version bumps and integration. Honor the resolved worker limit rather than a hardcoded engine ceiling. Verify actual model assignments, preserve current-model requests and restore temporary routing changes.

## Repository discipline

Work in the prepared branch/worktree. Preserve unrelated edits. Never auto-stash, reset, clean, overwrite the default branch or force-push. Commit coherent owned changes and their evidence; stage explicit paths and exclude private state. Preserve existing compatibility aliases and strong security behavior while replacing inconsistent internals. Publication and default-branch merge require explicit session authorization; the normal endpoint is a complete release candidate.

## Correctness and cost

Use one authoritative domain command path. Keep decisions immutable and applicability version-scoped. Reserve design spend atomically before dispatch. Unknown cost is not zero; uncertain provider outcome is not confirmed failure. Implementation spend is separate. A hard design cap requires controlled dispatch and bounded charges. Do not call paid external generation merely to test plumbing; deterministic fakes cover routine tests, with separately authorized live qualification where needed.

Pin worker inputs, artifact versions and evidence to the relevant scope. Permit explicitly owned new output paths. Keep repository roots distinct from run/storage roots. Preserve independent accepted components and referenced historical blobs.

## Verification and completion

Implement tests that exercise meaningful behavior and failure boundaries. A scenario document, mocked host, dry run, pack checker or screenshot alone cannot establish product completion. Preserve raw test reports privately; summaries retain commands, conditions, failures, hashes and limitations. Bind evidence to the current candidate; source changes invalidate affected evidence. Verify distributions in isolated installs, not only the checkout.

Use an independent reviewer when available. If unavailable, perform and label a separate sequential review with its limitations; never claim independence. Required defects and failed gates remain open. Human participant studies are deferred and must not be fabricated or converted into an unexpected blocking gate.

Update `.prism-state/progress.json`, task ownership, decisions, blockers and next actions after meaningful changes. On resume, reconcile actual artifacts and revisions before retrying expensive work. Stop futile identical retries; record the exact unresolved dependency while continuing independent tasks.

Finish only when the required scope, gate evidence, migration/rollback, installation, package parity, documentation and release-candidate outputs are complete. Report exact observed status and remaining limitations. Never mark completion merely because a checklist was populated.
