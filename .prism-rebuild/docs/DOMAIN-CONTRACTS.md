# Domain contracts and invariant ownership

Status: proposed runtime contract 2.0.0; pack version 1.0.0. The [JSON Schema](../contracts/domain.schema.json) defines record shapes. The [command catalog](../contracts/command-catalog.json) defines operation inputs and authority. This document defines semantic rules that a shape validator cannot establish. Target source code paths are identified explicitly; all document links are pack-relative.

## 1. Contract conventions

Runtime records carry `schemaVersion: "2.0.0"` and a `recordType` discriminator. Pack manifests use their own 1.0.0 version. Package version, protocol contract version, persisted schema version, entity revision and artifact version are different concepts; never compare them interchangeably.

Entity IDs are opaque portable strings generated by the core or the official client ID allocator and admitted by the core; they are not paths, timestamps, existing ownership or authority. Caller-supplied new IDs must be absent in the authorized namespace; collision never overwrites an existing entity. Mutable entity revisions are integers starting at 1. Artifact versions and decisions are immutable. Timestamps use UTC RFC3339 strings; sequence numbers/revisions, not wall-clock ordering, decide concurrent transitions. Reject duplicate JSON keys, NaN and Infinity before schema validation. Apply declared byte/count/text limits before expensive work.

`Money` is `{amountMinor, currencyCode, currencyExponent}`. `amountMinor` is an integer from 0 through 9,007,199,254,740,991; exponent declares how many decimal places the minor unit represents. For example, 1234 with USD/exponent 2 is 12.34 USD. The transport decoder requires an integer representation, not a binary float. JSON Schema defines integer mathematically and may accept `1.0`; the core therefore adds an exact-decoding check for money, revisions and counters. Python booleans are not accepted as integers. A three-letter format check does not prove a real currency/exponent pair; runtime validation checks the configured currency registry. No currency is inferred from locale, a dollar symbol or a previous project. Version 2.0 does not perform implicit foreign-exchange conversion.

Unknown costs use `CostObservation` with `status: "unknown"` and `amountMinor: null`. If an account establishes the currency, preserve it; for accountless work whose currency is also unknown, `currencyCode` and `currencyExponent` are both null. They are never partially known. Estimated, observed and explicitly not-billable amounts require a known currency/exponent and attributable source. An explicitly observed zero charge is different from unknown. Estimates do not become settled ledger entries merely because a task completed. Every amount displays its currency and certainty.

## 2. Entity boundaries

| Definition | Identity/revision and invariant owner |
|---|---|
| `Project`, `WorkspaceBinding` | Stable project identity is independent of source checkout path and Git. Binding contains local paths and storage assurance; it is private and rebound on import. |
| `ModelPreferenceSet`, `VersionedSnapshot` | Revisioned personal/project defaults and immutable input/policy snapshots. Existing runs retain their resolved policy when defaults change. |
| `Run` | Owns lifecycle, run type, decision mode, persisted resolved settings and declared scope. Its display stage is not an approval dependency. |
| `Component` | Stable design identity across revisions; parent and membership relationships are explicit. Retiring a component does not erase prior decisions. |
| `ArtifactVersion` | Exact immutable bytes, MIME type, dimensions, provenance and input dependencies. A new byte sequence is a new version. Availability/corruption is reported separately from historical identity. |
| `DependencyEdge` | A dependent version/scope names the exact prerequisite snapshot. Cycles are rejected for executable work graphs. |
| `ApprovalRequest` | Owns the reviewed scope, exact manifest, expected request revision, allowed actor policy and open/resolved/superseded/cancelled state. |
| `ApprovalDecision` | Immutable historical statement by an identified actor, for one request revision and exact fingerprint. It is not a mutable current-stage flag. |
| `ApprovalRevocation` | Explicit, authorized withdrawal with reason and scope, appended without rewriting the original decision. |
| `BatchReview` | Versioned collection of stable item/component/request identities. Decisions remain per item; batch membership revision is separate from item decision state. |
| `AnnotationSet` | Revisioned annotations on one immutable image/capture. Saved revisions are retained when referenced. |
| `RevisionRequest` | Exact base artifact and annotation-set revision, intended components, instructions and scope fingerprint. Never silently retarget to latest. |
| `BudgetAccount` | One explicit-currency design allowance per run, with enforcement prerequisites and a revision. Implementation/operations costs are outside its cap. |
| `BudgetReservation` | Atomic admission of a bounded design attempt; outstanding amount remains held while cost/outcome is unresolved. |
| `CostEntry` | Immutable observed debit/credit entry with category, amount, source and correction linkage. Estimates/unknowns belong in observations, not settled entries. |
| `ProviderAttempt` | One external execution attempt, request fingerprint, provider identity/receipt and separate execution/billing states. |
| `WorkerTask`, `WorkerLease` | Versioned work specification and exclusive attempt/fencing ownership. A lost lease does not establish remote failure. |
| `InstructionSnapshot` | Readable project/path instruction content, source scope, content digest and capture time. Host capabilities are separate grants, not copied hidden instructions. |
| `StageGateAssessment`, `EvidenceRecord` | Exact scope/criteria/input versions, required check identities, observed evidence and readiness. Unknown/deferred is never passed. |
| `OperationReceipt`, `DomainEvent` | Stable command result plus causal facts committed atomically with state. Side effects are not replayed during projection rebuild. |
| `CapabilityDescriptor`, `CapabilityGrant` | Observed API/host abilities, actual SQLite runtime/policy and supported limits versus scoped authorization. Tool presence is not permission. |
| `BlobStagingReceipt` | Principal/scope-bound temporary bytes with declared hash/size, verification status and expiry. It does not establish an available artifact. |
| `ExportManifest`, `MigrationReceipt` | Portable validated state/blobs and auditable migration phases. Private bindings, profiles and active capability material are excluded from portable exports. |
| `ThemeDescriptor`, `ThemeSelection` | Observed theme version/capabilities and an authorized reversible selection on an explicit dashboard, generated-product or OMP-host target. |
| `RunView`, `ApprovalView`, `BatchReviewView`, `BudgetSummary`, `ActionState` | Bounded read projections with freshness, scoped explanations and available actions. These are query results, not writable domain records or authorization grants. |

The target Python core owns all these invariants. Adapters can improve presentation or transport encoding; they cannot relax, duplicate or reinterpret them.

## 3. Command envelope, concurrency and idempotency

Canonical command inputs contain `command`, `operationId`, `idempotencyKey`, `actor`, `scope`, `expectedVersions` and `payload`. The server derives the authenticated actor and compares any asserted actor with it. `scope` contains project/run/component/artifact IDs and stage where relevant; null/empty scope fields are legal only for operations whose catalog entry permits them.

For a mutation, the idempotency key is required and scoped to owning realm + authenticated principal + command. The realm is a project ID or the principal's private local profile ID; null project scope does not merge all users into a shared namespace. Fingerprint the canonical command semantics: scope, expected versions and payload, excluding transport IDs/timestamps/tokens. A completed identical retry returns the original receipt even if revisions have since advanced. Reusing a key for another payload is `IDEMPOTENCY_CONFLICT`. An in-progress identical request returns its operation ID and status. Retain mutation keys for at least the retained lifetime of their run/ledger; a provider's shorter idempotency window does not change the local contract. `operation.get` retrieves the durable receipt under the original scope. `requestBlobSha256` preserves the normalized, secret-free request including its reason; audit detail is not reconstructed from a fingerprint alone.

Expected revisions protect mutable records. Exact version IDs/digests protect immutable artifacts and snapshots. Both are required where their concerns apply. Example: `approval.decide` checks the request's expected revision and the bound artifact/dependency fingerprint. It does not require the whole run record to remain byte-identical. A duplicate request with a new key is not automatically equivalent to retrying the old operation.

`EntityVersionRef` uses the record's revision, or its immutable version number for an artifact/snapshot. A one-time immutable fact without a version field, such as an approval decision, evidence record or revocation, uses revision 1 in references. The core validates the entity type/ID pair and rejects duplicate or conflicting expected-version entries. An absent entity on create is checked by the command's uniqueness constraint; do not encode absence as revision 0.

Errors use a stable code, user-readable message, bounded field errors, correlation ID, relevant current revisions when authorized, and retry advice (`none`, `refresh`, `backoff`, `reconcile`). A domain error is translated to appropriate HTTP/MCP/CLI representation. Never expose a traceback or secrets as the user error. Query results may add fields in a compatible minor revision; clients ignore unknown output fields. Strict command inputs reject unknown fields unless the contract explicitly reserves an extension field.

### Initialization, preferences and read surfaces

`project.initialize` resolves source and local-state locations from an existing workspace grant, records actual SQLite qualification, creates Project/WorkspaceBinding/default policy and criteria snapshots, and publishes a recoverable locator. It does not take an arbitrary path as authority or overwrite a legacy project. `snapshot.create` registers verified immutable requirement, criteria, policy or toolchain content; policy updates still require the policy's governing authority. Instruction capture is an internal step of project/work context preparation, using the actual scoped instruction files and their digests.

`model.preferences.get/update` targets either the authenticated principal's local profile or the current project. Each update replaces a complete preference set under an expected revision and appends its immutable snapshot. A personal update changes only the private profile store; a project update changes its preference record and `Project.defaultsSnapshotId` in the project transaction. There is no cross-store transaction. Resolve the documented precedence when creating/configuring a run, store the resulting policy and each origin, and preserve it on resume. Omitted `run.create.settings` uses defaults; supplied settings request a complete invocation override subject to actual authority. Changing defaults never edits a running or resumed run. Origin/capability assertions in input are recomputed by the core.

`run.get` returns a `RunView`, not a bare Run with undeclared extra fields. It has paged components and optional paged history, budget summary, relevant gate assessments, database epoch/event sequence, projection status, capability revision, `allowedActions` and per-command `actionStates`. Every disabled action has structured reasons. The allowed set equals the enabled action states for that authenticated scope. Approval, batch, gate, budget, artifact and operation queries provide focused views. Bounds/cursors prevent loading an entire history or all artifact bytes to refresh one panel. Queries never authorize a later mutation.

`run.advance` changes the display stage only after rechecking the specified current gate and allowed run-type transition. `run.complete` checks the agreed output/gate set and outstanding dispatch obligations. A design-only run does not require implementation gates. Unresolved billing may remain visibly held after a permitted handoff, but unknown execution that could still change the promised output prevents a false Completed claim. `run.configure` cannot substitute for stage advance or completion. Resume from `recovery_required` requires recorded recovery findings to be resolved.

The blob transport follows `blob.prepare` → authenticated bounded stream → `blob.verify` → `artifact.register`, `state.import_prepare` or `theme.install`. The stream is not a JSON command body. Staging IDs are principal/scope-bound, concurrent writers conflict, and verified staging cannot be replaced. Ready artifact metadata is published only after exact durable bytes exist. A same-ID retry never silently changes its declared digest or size.

## 4. Approval applicability algorithm

Create a request from a complete review manifest:

1. Target project/run, stage, scope purpose and sorted stable component IDs.
2. Exact primary artifact version/digest and every required artifact or source dependency snapshot.
3. Requirement/criteria snapshot and relevant design policy/instruction versions.
4. Any declared composition dependencies, selected theme inputs or toolchain snapshot whose change affects the promised result.

The server computes `scopeFingerprint` using a versioned deterministic manifest encoding. Proposed encoding `prism-approval-v2`: UTF8 canonical JSON of the explicit manifest, keys sorted by Unicode code point, integers only, no insignificant whitespace, stable escaping and deterministically sorted set-like arrays; hash with SHA-256 after the domain prefix `prism-approval-v2\n`. The authoritative Python encoder publishes test vectors. Clients consume the supplied fingerprint instead of inventing their own. Image annotation floating-point coordinates are excluded; their saved immutable annotation-set snapshot is referenced by ID/revision/digest where relevant.

Exclude progress, last-viewed time, display title, polling/watch timestamps, unrelated Git commit/dirty state and unrelated run artifacts. Changes to an excluded field do not invalidate the request. Do not exclude a genuine requirement or source input merely because it lives in `run.json`; migrate the meaningful field into the relevant versioned snapshot.

A decision is applicable only if:

- Its outcome is Approved and it is a verified decision, not an unverified import.
- Its actor was permitted at the recorded scope: human for Guided, or human/delegated agent for YOLO.
- Its request revision/fingerprint and referenced artifact bytes match the action's required manifest.
- The decision has not been explicitly revoked/superseded for that scope.
- Every required upstream design decision/check applies to the exact versions required now.

Record the failure as a structured reason such as changed artifact, changed prerequisite, changed criteria, revoked authority, missing blob or unverified legacy evidence. Show the historical decision alongside its present applicability. Do not rewrite “approved” history to pretend it never happened.

Stored `feedback` is an ordinary bounded string. An empty string is valid for human Approved. Inputs may omit optional feedback or supply null, empty or whitespace; normalize all of these to `""` consistently in the core. Changes Requested must include actionable text or at least one valid annotation reference; Rejected requires an explanatory reason. A delegated agent approval also records a nonempty decision explanation. A mode switch never retroactively changes the actor of an old decision. An agent cannot fabricate a human approval in Guided mode.

## 5. Stable partial batch decisions

`component.decompose` creates stable component IDs and explicit dependencies; renaming or revising a component does not replace its identity. `approval.batch_request` then creates or explicitly revises a `BatchReview` from existing exact approval requests. Stable item IDs reference component, request and artifact versions. Its revision changes only when the membership/review manifest changes, not whenever an item is decided. Duplicate item/component identities or request versions outside the declared scope are rejected.

`approval.batch_decide` accepts a batch revision and a list of item decisions, each with an expected request revision. The outer authorization/shape/batch check occurs first. Then each item runs the same decision handler as a single-item decision. Expected item conflicts become per-item results: Applied, Conflict, Forbidden or Invalid. Applied results commit together with those outcomes and one batch receipt in a short local transaction; no external calls occur inside it. An unexpected storage/internal error aborts the transaction rather than claiming a partially committed unknown result.

This is **partial acceptance semantics**, with a durable single receipt: one stale component does not prevent valid independent decisions, while a process crash cannot leave an unrecorded subset. Identical retry returns the same receipt. Retrying conflicted items after refreshing uses a new operation/key. Never silently replace the stale item with its newest request or flatten all items into one stage-wide decision. A changed batch manifest returns `VERSION_CONFLICT` before item application.

Composition remains a separate scope. Approving all children does not imply their combined layout, integration or accessibility passed. Conversely, requesting changes to one child preserves accepted independent siblings.

## 6. Exact-image annotations and revision lineage

`AnnotationSet` uses `baseArtifactVersionId`, `baseArtifactSha256`, `imageSize: {widthPx,heightPx}`, `coordinateSpace: "normalized_image"`, optional capture viewport/device-pixel-ratio metadata, and a revision. Coordinates refer to the actual displayed image content after letterboxing/cropping transforms are accounted for, never the containing stage. An HTML/PDF review uses a captured image stored as its own immutable artifact version, with a dependency on the source artifact.

Point objects contain finite `x,y` values in [0,1]. Line, arrow, rectangle and ellipse contain exactly two points: pointer-down and the latest endpoint. Pin contains one point. Freehand contains 2–128 points. A set contains at most 256 annotations and annotation text at most 4000 characters. These are contract ceilings, advertised in capability metadata; clients honor the lower applicable policy limit.

The client preserves the unsaved draft and shows the simplified result before save when freehand sampling exceeds the limit. Use a deterministic simplification method and consistent bounds; never silently discard trailing points. If a usable representation cannot fit, return an actionable field error while preserving the draft. Server validation enforces the same limits. Each annotation has an accessible textual description; drawing is not the only way to communicate a requested change.

`RevisionRequest` pins the base artifact/digest, annotation set ID/revision, selected component IDs and instructions. The implementation verifies they belong to the same scope and image. A new render or dimension change requires an explicit new annotation set or deliberate rebasing operation with a visible preview; never transform old annotations silently onto new bytes. Revision results produce new artifact versions linked to the request and original base. Completing generation creates Ready for Review, not automatic human approval.

## 7. Design budget and attempt state machines

`BudgetAccount.enforcement` is `hard`, `advisory` or `unbounded`. A Hard account requires a non-null cap, controlled dispatch, and supported charge bounds. Advisory can record estimates and locally stop admission but cannot promise that out-of-band charges are blocked. Unbounded requires an explicit configuration; absence of a budget is not the same as unlimited authorization. Currency/exponent cannot change after ledger/reservation activity; create a new explicitly reconciled account instead.

Version 2.0's guaranteed cap is per-run design spend. A future project-wide cap must coordinate all relevant reservations in one authoritative transaction; it must not be inferred by adding unsynchronized run totals. Design generation and design revision count toward the cap. Critique follows the persisted run setting. Implementation, infrastructure and this pack's production are separately classified and excluded by default. The core derives/validates task category from the authorized work and policy; a worker cannot relabel a design operation to bypass admission. The duplicated critique setting in Run and BudgetAccount is updated atomically with the relevant revisions.

`budget.adjust` appends a refund, correction or reclassification with evidence and linked original entries. A refund is a verified credit; a correction is the supported signed delta. Reclassification writes an equal credit and debit in the same currency/amount, preserving the original category history. All legs commit together and require category-change authority. Reject repeated provider receipts, cross-run/currency links and reversal beyond the original unreversed charge. Never edit a historical cost or discard a real additional debit merely because it breaches the cap. `BudgetSummary.availableMinor` may be negative for a real breach; this blocks further design dispatch and remains visible.

Reservation states are `held`, `dispatched`, `unknown`, `settled`, `released`. Held capacity counts immediately. Dispatched/Unknown continues to count at its remaining bound. A release is allowed only before dispatch or after authoritative evidence of no remaining charge liability. Settlement records actual debit/credit entries and releases only the resolved excess. Cancellation does not itself authorize release.

Provider execution states are `prepared`, `dispatching`, `running`, `succeeded`, `failed`, `cancel_requested`, `cancelled`, `outcome_unknown`. Billing has its separate `CostObservation`. Execution can be terminal while billing is unknown. A request may succeed and still require billing reconciliation; a failed/cancelled request may incur cost.

The canonical start sequence is `work.plan` → `provider.prepare` → `budget.reserve` when design exposure requires admission → `work.dispatch`. Prepare creates the attempt and binds its task, exact request fingerprint, model resolution, provider capability snapshot and price quote without calling the generation endpoint. Dispatch transactionally claims a fresh fenced lease and consumes the permitted reservation before making the external call. `work.heartbeat` renews only the active owner/lease under its expected revision; the core sets expiry using its configured bounded policy. A stale heartbeat/result never revives a replaced lease. `work.record_outcome` and `provider.reconcile` distinguish actual execution, observed model and billing state. Provider evidence/price capability capture is adapter-derived, not a caller-supplied claim of a hard charge bound.

For an amount `R` requested against cap `C`, settled design consumption `S` and outstanding reservations `H`, admission checks `S + H + R <= C` and records the reservation atomically. Two concurrent requests for8 units with10 left admit at most one. Same-key replay does not reserve twice. Maintain each account in one currency/exponent. Reject mixed currency or stale/unbounded price assumptions before claiming Hard admission. If prices lack a verified charge ceiling, the policy is Advisory or dispatch is blocked pending an allowed route.

Do not silently launch a second attempt after timeout. Query provider status by stable execution identity if supported; otherwise retain Unknown and request the appropriate reconciliation within existing authority. Retrying safely under a still-valid provider idempotency contract can reuse the external request identity; if that guarantee is absent/expired, a new attempt requires separate admitted exposure. Record original and actual model/provider identities, price quote and observed usage; do not assume an assignment succeeded because it was requested.

## 8. Scope-specific stage gates and evidence

`StageGateAssessment` records the stage, exact scope fingerprint, criteria snapshot, required check IDs, check results, approval decision IDs, dependency references, and readiness. A check result includes evidence IDs and status `passed`, `failed`, `unknown`, `deferred` or `not_applicable`. A gate can be `ready`, `blocked`, `waiting` or `deferred`; explanation codes accompany it.

`evidence.record` is the canonical creation path for observations. The core binds the authenticated observer, exact subject versions, method, time and retained artifact/operation evidence. `work.record_outcome` may refer to those existing IDs; it does not manufacture prior observations. `EvidenceRecord.operationId` refers to the observed operation, while the enclosing event/receipt identifies the command that recorded the evidence. Corrected/repeated observations append new IDs with their provenance. Agent text or imported history cannot claim that a human study occurred.

Readiness is a deterministic function of the recorded policy and current authoritative inputs:

1. Materialize the required check **set**, not a message count. Check IDs are unique within the criteria snapshot.
2. Match evidence to the same subject/version, method and relevant environment. Duplicate delivery cannot satisfy a missing check.
3. Require current applicable decisions for the gate's scope, using the mode's actor rules.
4. Require all mandatory checks to pass. Failed blocks; missing/unknown waits or blocks as specified. Not Applicable needs a policy-supported reason.
5. Deferred work remains Deferred. An explicit release policy may exclude deferred human research from the current release gate, but its result must still be reported as unperformed. It cannot be counted as a pass or used to claim validated usability.
6. Bind the result to its exact dependencies; reevaluate only affected scopes when they change.

`assess` concerns an actual assessment and known scope; `plan` concerns selected direction and dependencies; `design` concerns the complete required mockup/component set; `produce` concerns implementation/integration where requested; `finalize` concerns the agreed run type's handoff and relevant checks. A structural checker establishes structural completeness/currentness only. It does not prove visual quality, real host integration, accessibility conformance, publication or user research.

### Theme target contracts

`ThemeTarget` contains `themeScope` (`dashboard`, `generated_product`, `omp_host`) and an opaque registered `targetId`. A descriptor reports observed version and supported actions. `theme.list/inspect/preview/install/activate/restore/uninstall` are distinct operations, enabled only when the target capability exists. Dashboard appearance may select a built-in or installed theme without a design run or decision. Generated-product activation requires the exact theme artifact, run and applicable design decision. OMP-host installation/activation requires the actual host interface and explicit target authority; it is never implied by a colour preference.

Every mutation checks the target fingerprint and relevant selection/version. Preview does not install or activate. Installation is owned and reversible, with a validated package and receipt; generated product tokens use artifact registration rather than host installation. Uninstall requires the matching owned installation receipt and cannot remove the active theme until a permitted replacement/restore occurs. Restore refuses divergent later edits. Neither dashboard appearance nor host selection rewrites artifact bytes or historical decisions.

## 9. Cross-record semantic checks beyond JSON Schema

The engine must enforce foreign-key ownership, per-component uniqueness inside batches, acyclic dependency graphs, artifact byte/dimension matches, expected revisions, actual authority, immutable history, category/currency consistency, ledger sums, prerequisite applicability, same-image annotation references, unique required check sets, safe paths and lease fencing. JSON Schema validates local shape and some conditional fields; it cannot check another row or the filesystem.

The fixtures in [examples](../contracts/examples/manifest.json) deliberately cover schema validity. Acceptance cases cover semantic and crash/concurrency behavior separately. A valid fixture is not a functioning workflow, and a schema-valid approval is not proof of human authorization.

## 10. Distilled source basis and rejected assumptions

The invariant/identity choices synthesize Vernon's *Domain-Driven Design Distilled* (2016), PDF pp.41–45,71–83,89–99; Stopford's *Designing Event-Driven Systems* (2018), PDF pp.120–124,126–135,157–163; and Xu's *System Design Interview*, second edition, PDF pp.66,229–235,251–260. These are sources for reasoning, not copied specifications. We reject a mandatory class model, stage-wide mutable fingerprints, raw-event-count gates, a rate limiter as a money ledger, last-N deletion of referenced evidence, and unqualified exactly-once promises for external calls.

Primary implementation references: [SQLite transaction visibility](https://www.sqlite.org/isolation.html), [Kafka delivery semantics and external cooperation](https://kafka.apache.org/42/design/design/), and [JSON Schema Draft2020-12](https://json-schema.org/draft/2020-12). Core behavior above is a proposed project policy and must be verified by implementation tests.
